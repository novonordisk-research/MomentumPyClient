# MomentumPyClient Security Issues

_Produced in Step 2. Reviewed by JSQP and a Biophysics group member before use._
_Living document — update entries as issues are resolved._

## Issues

| # | Description | Severity | File / Line | Status |
|---|-------------|----------|-------------|--------|
| 1 | **SSL verification disabled by default.** The `verify` parameter defaults to `False` when not specified in constructor arguments or `.env`. `disable_warnings(InsecureRequestWarning)` is also called, which suppresses the runtime warning that would otherwise alert developers. All API traffic — including the authentication token exchange — travels without certificate validation. Any attacker with network access between the client and the Momentum server can intercept credentials and tokens. This is particularly relevant on a shared lab network. The correct default is `verify=True`; `False` should only be used as an explicit opt-in with a documented reason. | High | `ws.py:129–131` | Open |
| 2 | **Credentials stored in plaintext `.env` file.** The package reads `momentum_user` and `momentum_passwd` from a `.env` file via `python-dotenv`. The `.env` file typically sits in the working directory alongside application code. If this directory is version-controlled, credentials can be accidentally committed. The repository's `.gitignore` is not guaranteed to exclude `.env` files in downstream projects. Additionally, `.env` files have no access controls beyond filesystem permissions. Rotating credentials requires a manual file edit. | Medium | `ws.py:98–110`, `app_config.py:4–6`, `.env` (not in repo) | Open |
| 3 | **Password stored on the instance.** After construction, `self.password` (the plaintext password) remains as an attribute on the `Momentum` instance for the lifetime of the object. Any code that can access the `Momentum` instance can read the password via `m.password`. The `self.login` dict (also on the instance) holds a copy as `self.login["Password"]`. This makes credential exposure more likely in debug sessions, logging of object state, or accidental serialisation. The token should be the only credential kept post-authentication; the password should be discarded after `_get_token` is first called. | Medium | `ws.py:109–117, 139` | Open |
| 4 | **Token stored on the instance without expiry tracking.** `self._token` is set and refreshed but the expiry time is not recorded. The auto-refresh logic in `_send_get_request` triggers only on a 401 response. There is no proactive token refresh before expiry. For POST and DELETE requests there is no retry-on-401 logic at all — an expired token will simply raise an exception. This is a reliability concern more than a security concern, but it means an expired token during a POST could leave a job submission in an unknown state. | Low | `ws.py:143–200` | Open |
| 5 | **Error message in `_send_post_request` exposes the full request body.** When a POST returns an unexpected status code, the exception message is `f"Error {resp.status_code}: {resp.text} posting {url} with {data}"`. If `data` contains sensitive information (currently variable values such as file paths, not credentials), this could appear in logs. The `_get_token` method specifically avoids this pattern with a comment: "do not use the `_send_post_request` method here, because it will show username and password in the error message" — the same caution should be documented for any future callers who pass credential-like data to `_send_post_request`. | Low | `ws.py:197–200` | Open |
| 6 | **Hardcoded internal server hostname in `app_config.py`.** The file `app_config.py` in the Streamlit app contains hardcoded internal server hostnames (`lpdkhqgm150ntv`, `lpdkhqEM00P3W7`). These are not credentials but represent internal infrastructure topology. If this file is committed to a repository with broader access, it constitutes minor information exposure. Hostnames should be environment-configured, not hardcoded. | Low | `app_config.py:13, 20` (in momentum-streamlit, not in MomentumPyClient itself) | Open |
| 7 | **No input sanitisation on XML-building methods.** `create_worklist_xml`, `run_process`, and `run_experiment` build XML using `xml.etree.ElementTree` with user-supplied strings as element text and attribute values. `ET` escapes text content automatically, so standard XML injection into element text is mitigated. However, attribute values (e.g., process name, batch name, workunit name) are passed directly as XML attribute strings. ET also escapes these, so the risk is low in practice, but it is worth noting that process names and batch names are not validated against any allowlist. A malformed name could cause Momentum to reject the worklist in unexpected ways. | Low | `ws.py:418–469, 484–588, 590–643` | Open |
